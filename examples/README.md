# Example bundles — one program, all the way through

Generated by `make examples`. **Committed rather than regenerated**, so that a
consumer in another repository needs neither SDCC nor a `stc-compiler` checkout
to open one.

Every layer of this project had tests of its own before these existed — the
emitter's round-trip tests, the emulators' differential execution, the board
layer's scripted MCU, the monitor's command-layer tests. None of them tested
whether the layers **compose**, because nothing produced an artefact all of
them consume. A bundle is that artefact.

## What is in one

| file | what reads it |
|---|---|
| `<name>.bw` | the source, copied in so the bundle stands alone |
| `<name>.c` | what the emitter produced — the translation stays inspectable |
| `<name>.hex` | ready for `stcgal`, and for both emulators |
| `<name>.cdb` | SDCC debug info; `symbols.json` is derived from it |
| `pins.json` | **boundary C** input: `{device, clock, pins}` → `inferNetlist` → a board to draw |
| `symbols.json` | **boundary D** input: where `bw_ms` and each `<task>_state` live, plus every yield point's code address. Multi-`WHEN` programs only |
| `meta.json` | sizes, task count, and which `inferNetlist` rows the example exercises |

`manifest.json` at the top level aggregates all of them.

## The set, and why it is this set

| example | tasks | covers |
|---|---|---|
| `01-blink` | 1 | `OUTPUT ACTIVE LOW`. The smoke test — two LEDs, nothing else. |
| `02-button` | 1 | `INPUT` with a pull-up, plus debounce and `REPEAT UNTIL` |
| `03-potentiometer` | 1 | `ANALOG` — the ADC path, still unverified on silicon |
| `04-brightness` | 1 | `OUTPUT` active-high, deliberately the *wrong* wiring, next to a right one |
| `05-scheduler` | **2** | the cooperative scheduler, and the only bundle with a `symbols.json` |

Between them they exercise **all four** `inferNetlist` rows in
`sb3-creator/reference/simulation-contract.md` boundary C. The builder fails if
that stops being true — a circuit designer with a preset and no example behind
it is a preset nobody has ever run.

Two of these earn their place beyond coverage:

**`04-brightness`** drives an active-low and an active-high LED together, and
they will not look the same: a quasi-bidirectional pin sinks 20 mA but sources
about 230 µA. The whole active-low convention in this repo follows from that
asymmetry, and this is the example that lets the simulator *show* it instead of
asserting it. It is the one place the wrong wiring is on purpose.

**`05-scheduler`** is what the debugger is aimed at. Two scripts at 500 ms and
300 ms — deliberately not multiples, so a scheduler bug that couples the tasks
is visible within seconds. Its `symbols.json` is what lets a debugger answer
"where is the program" by reading three variables, and what a yield breakpoint
resolves through.

## What the set cannot cover yet, and why that matters

Everything here is GPIO and the ADC, because that is everything the emitter
emits. The circuit designer needs more than that, and the gaps are specific:

| missing | blocked on | the example it would unlock |
|---|---|---|
| **PWM** | PCA blocks in `stc_pseudocode.py`; `STC12-PERIPHERAL-MODEL.md` §5 is a skeleton | LED dimming and a buzzer tone — the two transducers `simulation-contract.md` boundary B already specifies (`ledBrightness`, `buzzerTone`) and nothing exercises |
| **UART output** | emitter support | a serial console part, and the tethered-mode link |
| **Motor / H-bridge** | PWM, plus board parts | the case where `branchCurrent` forces a real solver rather than the closed-form fast path |

That last column is the point. `ledBrightness` is specified as *current × PWM
duty integrated over ~20 ms*, and no example currently produces a duty cycle at
all — so half of that contract has never been exercised by anything. **The next
slices should be peripheral-driven rather than wiring-driven**: the four
`inferNetlist` rows are covered, the transducers are not.

## Regenerating

```bash
make examples
```

Needs SDCC and `../stc-compiler`. The builder is a developer tool; nothing in
the firmware build depends on it. If a bundle changes when you did not expect
it to, that is the emitter changing under you — which is worth knowing.
